## 1. 背景与问题定义

用户观察：启动一个 Grok 新会话的固定上下文开销约 15k tokens，认为偏多。由此引出四个问题：

| # | 问题 | 本文件回答 |
|---|---|---|
| Q1 | 15k 由什么构成？是否过多？ | §3：大头是 MCP 工具 schema，不是 SKILL |
| Q2 | 2026-09-24 的族群化是否失效（manual 成员仍被注入）？ | §3.2：**未失效**，23 条 manual 均不在会话技能清单 |
| Q3 | MDLineage 能否降低 SKILL 上下文占用？ | §7：不能降启动 token；价值在创作期治理 |
| Q4 | 不属任何族群的独立技能能否标记为"全 Agent 可见但不进启动清单"？ | §4/§6-P2：当前是**写入路径缺口**，方案为 `manual_standalone` 机制 |

**管理口径澄清**（2026-10-14 与用户对齐）：本农场管理的资产不只是 SKILL——`registry.yaml` 登记了模型渠道、MCP server、外部 CLI、App 自管根、本地服务共七类（§3.6）。上下文优化是其中的一个维度，不是全部；治理面（版本漂移、计数基线、死链）由既有 `assets-doctor` 循环覆盖。

**约束**（用户定调）：
- 农场不挑 Agent：所有 Agent 平等接入（软链农场语义保持）。
- 优化目标对象是"进系统提示的量"，不是"技能总数"。

## 2. 运行机制：启动上下文如何被拼装（以 Grok CLI 为例）

### 2.1 技能发现与注入

**发现路径与优先级**（`~/.grok/docs/user-guide/08-skills.md` L19-31，实测验证）：

| 位置 | 作用域 | 优先级 |
|---|---|---|
| `./.grok/skills/`（CWD） | Local | 最高 |
| `<repo_root>/.grok/skills/` | Repo | 中 |
| `~/.grok/skills/`（**软链农场挂载点**） | User | 低 |
| `~/.grok/bundled/skills/` | App 自带 | 被同名的 local/repo/user 覆盖 |

另有兼容扫描：每层级同时扫 `.agents/skills/`、`.claude/skills/`、`.cursor/skills/`，并沿 CWD→repo root 逐级上溯。同名去重，高优先级覆盖低优先级。

**信任门禁**：不受信任目录里的项目级技能在启动发现时被**跳过**（08-skills.md L3；实测 `/tmp/skillprobe` 建的探针技能因 `Project trusted: no` 未被发现）。信任清单在 `~/.grok/trusted_folders.toml`（现 4 个目录，含本仓库）。

**注入的是什么**：启动清单只含 `name + description`（description 驱动自动触发）。SKILL.md **正文不进启动清单**——命中后按需 Read（单次读取上限 25k tokens）。这是 Q3 论证的前提。

**控制注入的三个开关**：
- frontmatter `disable-model-invocation: true`：模型不能自动触发，仅 `/name` 显式调用（挡的是"自动触发"，不挡"可见性"）。
- `metadata.load-mode: manual/auto`：农场自描述标记，**客户端不消费**（纯声明、零 token）；与 dmi 双写并由校验链保证一致。
- `~/.grok/config.toml [skills]` 三键：`ignore`（按路径前缀彻底隐藏）、`disabled`（列出但排除出系统提示与调用）、`paths`（追加扫描目录，来源标 `config`）。
- 注意：技能发现**不读 .gitignore**；想隐藏技能只能用 `[skills] ignore`。

### 2.2 MCP 工具注入（本机版行为）

MCP server 的来源五类（本机全部出现）：

| 来源 | 实例 | 可静态治理 |
|---|---|---|
| `~/.grok/config.toml [mcp_servers]` | zai-web-search、zai-vision（enabled=false）、thesis-exp | ✅ |
| `~/.claude.json` 兼容读取 | codegraph、keenable、vision | ✅ |
| Claude 插件 | context7 | ✅（插件开关） |
| 项目 `.mcp.json` | （当前无） | ✅ |
| **会话注入（无本地配置源）** | **github(98 工具)、tasks(10 工具)** | ❌ `registry.yaml` L134 已登记为 `session_injected_mcp`，doctor 只做"出现即提示" |

工具 schema 注入系统提示。当前版本无延迟加载/分页证据（是否截断待 P0 实测，见 §8-Q1）。

### 2.3 其它注入面

- 项目指令：`AGENT.md`（dc-skills，2,949B，信任目录内自动加载；`CLAUDE.md`/`AGENTS.md` 为兼容软链）。
- 全局指令：`~/.claude/CLAUDE.md`（1,752B ≈ 438 tokens，vendor=claude 兼容启用）。
- memory 索引：`MEMORY.md`（891B）。
- SessionStart hooks：Orca 条件钩子（`grok-hook.sh`，输出型，注入量取决于告警内容）。

### 2.4 农场在注入链中的角色

软链农场只决定"**哪些技能目录出现在 user 层**"（`agent-map.yaml` → `skills-sync` 物化）。注入量由三层杠杆决定：
1. **挂不挂**：base/on_demand/extra/preset 清单（可见性）。
2. **描述多长**：入口 description 的字符量（唯一进启动清单的 SKILL 内容）。
3. **auto 还是 manual**：族群标记三件套（`metadata.load-mode` + `disable-model-invocation` + Codex `agents/openai.yaml`）。

## 5. 方案总纲（GPT-6 仲裁 + 修正）

**总方针：先测量，再裁剪 MCP；族群架构保留；机制补全（P2）与 token 优化（P0/P1）分开推进。**

| 候选动作 | 裁决 | 理由（一句话） |
|---|---|---|
| A. MCP 排查与裁剪 | **采纳**（范围修正） | 最大潜在收益；但 github/tasks 已确认是会话注入（registry L134），若 Grok 不提供开关则该 108 工具进入"不可优化"清单，P0 上限受制 |
| B. bundled 扩大禁用 | **采纳，分批** | 16 个在注入；先禁确认无流程依赖的，按使用记录定名单，不预设"只留 3-5 个" |
| C. `manual_standalone` 机制 | **采纳** | 补机制债（即期 token≈0），顺带修复 D1/D2 两处漂移 |
| D. MDLineage 结合 | **拆分** | 创作期治理采纳；会话期 mdlineage-mcp 检索层搁置（常驻 schema 开销 vs 命中率未证）；"manifest 替正文省启动 token"**否决**（正文本就不进启动清单） |
| E. 入口 description 瘦身 | **采纳** | 每条 <300 字符为目标，保留触发条件/边界/路由信息；不为达标损害辨识度 |

**风险红线**：不绕过唯一事实源直接改软链产物；manual 不得变成不可见或不可 `/name` 调用；每批改动留回滚点；`skills-sync --check`、`skillctl lint`、CI、5-Agent 验收任一失败即停。

## 7. 与 MDLineage 的结合边界（Q3 的完整论证）

1. **不能降启动 token**：manifest 是构建期/校验期元数据，默认不进上下文；且 SKILL.md 正文本就不进启动清单（仅 description 进）——"用 manifest 替代正文省 token"优化的是不存在的开销（三方一致，GPT-6 否决）。
2. **创作期治理价值（采纳）**：relations 图 + MDL301/302/305/306（重复 id/悬空/环/废弃依赖）恰好覆盖农场最脆弱的面——入口路由表指向的成员被改名/移动时的静默失效；`WorkspaceIndex` 反向依赖可答"改这个 SKILL 会影响谁"。
3. **会话期检索层（搁置）**：`mdlineage-mcp` 作为按需检索层在原理上可行（启动清单只留极简索引，详情按需拉取），但新增 2-5 个常驻工具 schema（≈0.5k-1.5k tokens）且命中率未证——搁置，待有真实"跨技能导航"高频场景再评估。
