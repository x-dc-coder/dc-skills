## 一、统一平台定位与三层架构

### 1.1 平台演进定位

在过去的农场架构中，`dc-skills` 本质上是一个单向的“本地技能软链分发器”：它仅扫描项目目录下的 `SKILL.md`，并通过软链接将其挂载至各 Agent（Claude Code、Grok、Codex、DSH、Orca 等）的配置目录。随着全机能力的爆发式增长，这种简单模式暴露出以下系统性缺陷：
1. **资产碎片化**：MCP 服务器独立分散配置于 `~/.claude.json`、`~/.grok/config.toml` 中，缺乏与技能的绑定与版本基线管理；
2. **上下文膨胀失控**：各 Agent 盲目将所有挂载技能塞入模型启动清单（System Prompt），造成会话启动即消耗数万 Token，侵蚀有效推理窗口；
3. **命名空间冲突与阴影覆盖**：平台内置技能（Bundled）与插件技能（Plugin）同名竞态，缺乏全机全局索引与仲裁机制；
4. **项目指令分裂**：`CLAUDE.md`、`AGENT.md`、`AGENTS.md` 规范不一，指令与知识混杂。

因此，`dc-skills` 正式定位于全机唯一的**“全能力资产治理平台（Universal Capability Platform）”**。它将技能（Skill）、协议服务器（MCP）、执行工具（CLI）以及项目指令（AGENTS.md）统一收纳进标准化治理体系。

```
┌────────────────────────────────────────────────────────────────────────┐
│                        声明层 (Specification Layer)                     │
│    agent-map.yaml (期望态 / 拓扑分发)   registry.yaml (断言 / 健康基线)    │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 编译驱动 / 消费
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                         编译层 (Compilation Layer)                      │
│   skills-sync (软链物化)   family-apply (标记与模式)   mcp-apply (标记块分发)  │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 生成物化与配置
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│                         巡检层 (Inspection Layer)                       │
│      assets-doctor (CI 闸门 / 静态对账 / 漂移阻断 / 退出码 0-3 级联)       │
└────────────────────────────────────────────────────────────────────────┘
```

### 1.2 三层架构体系职责与边界

全能力治理平台严格遵循三层分立架构，禁止层级倒置与跨层越权：

| 架构层级 | 核心组件 | 输入源 | 输出产物 / 作用域 | 核心职责与设计约束 |
|---|---|---|---|---|
| **声明层 (Spec Layer)** | `agent-map.yaml`<br>`registry.yaml` | 架构师与开发者的人工声明 | 期望态字典、静态断言规则、健康阈值 | **全机唯一事实源**。声明全机技能分发、族群依赖（CLI/MCP）、加载模式（auto/manual）及资产探测基线。严禁包含运行时动态生成逻辑。 |
| **编译层 (Compile Layer)** | `scripts/skills-sync`<br>`scripts/family-apply.py`<br>`scripts/mcp-apply.py` | 声明层清单、主库物理资产 | 软链农场（`~/.<agent>/skills/`）、元数据标记、客户端配置（`~/.grok/config.toml`、`~/.claude.json` 等） | **确定性物化编译器**。将期望态物化为各 Agent 原生可识别的物理结构。必须具备幂等性、Dry-run 预检能力与安全标记块（Managed Blocks）保护机制，严禁破坏宿主私有配置。 |
| **巡检层 (Inspect Layer)** | `scripts/assets-doctor` | 声明层期望态、实际物理文件系统、网络端点 | 结构化终端报告、JSON 审计报告、进程退出码 | **自动化质检验收与防退化网**。负责静态契约校验、软链漂移比对、外部工具可用性探测、MCP 健康度探测与阴影覆盖预警。具备分级阻断能力。 |

## 二、全机技能三桶治理模型

为彻底终结全机技能分散、冲突与失控状态，全机所有技能划入**“三桶模型（Three-Bucket Governance Model）”**进行全生命周期纳管。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                             全机技能三桶治理模型                         │
├──────────────────────────┬─────────────────────────┬────────────────────┤
│   第一桶：主库托管技能   │   第二桶：平台内置技能   │ 第三桶：外部插件技能 │
│  (Managed Base/Extra)    │    (Platform Bundled)   │ (External/Plugins) │
├──────────────────────────┼─────────────────────────┼────────────────────┤
│ • 物理路径：主库根目录    │ • 典型路径：            │ • 典型路径：        │
│ • 总数：34 个技能        │   ~/.grok/bundled/      │   ~/.codex/plugins/│
│   - 12 个 entry 入口     │ • 总数：22 个技能       │   ~/.claude/plugins│
│   - 22 个 member 成员    │ • 治理动作：            │   ~/.dsh/cordis     │
│ • 交付机制：软链农场分发 │   - 禁用 3 个 (白菜/同名)│ • 总数：25+2+2     │
│ • 控制模式：auto / manual│   - 保留 19 个原生能力  │ • 治理动作：只读索引│
│ • 状态：完全掌控、单拷贝 │ • 状态：被动基线、覆写隔离│ • 状态：命名空间隔离│
└──────────────────────────┴─────────────────────────┴────────────────────┘
```

### 2.1 第一桶：主库托管技能（Managed Base / Extra）

- **定义与物理存储**：存放在主库 `/home/dc/projects/dc-skills/` 根目录下的独立子目录，是本机自主研发、维护与治理的核心资产。
- **全机规模**：共计 **33 个物理技能**，严格遵循单物理副本原则，各 Agent 仅通过软链接可见。
- **结构化划分**：
  - **11 个 Entry 入口技能（`role: entry`，默认 `load: auto`）**：
    负责承接用户意图与顶层路由，其 `SKILL.md` 的 description 必须精简至 300 字符以内，保持低 Token 占用。包含：`diagram`、`design-ui`、`thesis-writing`、`programming`、`orca-cli`、`unified-search`、`db-skill`、`wsl-windows-bridge`、`lark-cli`、`dsh-plugin-troubleshooting`、`dc-skill-creator`。
  - **20 个 Member 族内成员技能（`role: member`，默认 `load: manual`）**：
    专注于纵深执行，默认不注入 Agent 启动上下文，通过 `metadata.disable-model-invocation: true` 和 `agents/openai.yaml` 声明模型静默，仅在收到 `/name` 指令或由 Entry 技能通过路由逻辑显式读取时加载。包含：`drawio-xml`、`design-diagram`、`design-dataviz`、`thesis-ref-check`、`md-to-thesis-latex`、`paper-metrics`、`paper-reader`、`debugging`、`git-master`、`remove-ai-slops`、`test-guardian`、`github-workflow`、`codegraph-explore`、`orchestration`、`task-hub`、`computer-use`、`cloudreve-storage`、`kimi-webbridge`、`vision-workflow`、`dsh-ui-optimization`。
  - **2 个 Standalone 单体技能（`role: standalone`，默认 `load: manual`）**：
    不隶属族群，经 `/name` 显式触发。包含：`proxy-ops`（梯子运维）、`word-extractor`（.docx 提取，2026-10-15 docs 族解散后由 member 转入）。
- **分发控制机制**：统一由 `agent-map.yaml` 中的 `base` 与 `extra` 段定义分发矩阵，由 `scripts/skills-sync` 进行确定性软链物化。

### 2.2 第二桶：平台内置技能（Platform Bundled）

- **定义与物理存储**：由客户端宿主应用程序安装包自带、随 App 版本升级而自动分发的出厂技能。典型路径为 `~/.grok/bundled/skills/`（共 22 个技能）以及 Codex 自带的系统技能 `~/.codex/skills/.system/`。
- **核心风险**：
  1. **低质与冲突**：部分内置技能与主库高质量技能同名，但其实现简陋且上下文消耗巨大（例如自带的 `docx`、`pptx`、`create-skill`）；
  2. **版本不可控**：App 静默升级时可能重置或新增内置技能，冲刷自定义设置。
- **治理策略与硬性处置**：
  - **显式禁用（3 个同名与劣质技能）**：
    在 `~/.grok/config.toml` 的 `[skills]` 段配置 `disabled = ["create-skill", "docx", "pptx"]`。
    - `create-skill` 禁用：主库具备全机规范生成器 `dc-skill-creator`，禁止内置简陋生成器干扰；
    - `docx` 禁用：主库具备 `word-extractor`（officecli 已于 2026-10-15 归档），禁用内置脚本；
    - `pptx` 禁用：同上，收敛至主库 Office 工具链。
  - **保留并纳管（19 个平台特有能力）**：
    保留如 `code-review`、`design`、`execute-plan`、`game-assets`、`threejs-frame-conventions` 等 19 个平台特化技能。
  - **同名竞态防范原则（Precedence & Shadowing Rules）**：
    各 Agent 载入路径中，若主库挂载技能与 Bundled 技能同名，必须在客户端配置中将农场软链目录优先级置于 Bundled 之上，或在配置中显式将冲突项加入 `disabled` 列表。禁止在农场中创建与保留技能冲突的未受控名称。

### 2.3 第三桶：外部与插件技能（External / Plugin Skills）

- **定义与物理存储**：用户通过各客户端生态市场、插件系统或实验性预设安装的第三方技能。
  - **Codex 插件缓存**：`~/.codex/plugins/cache/`（当前包含 25 个模板与插件技能，如 `openai-templates` 系列、`work-pets`、`sites` 等）；
  - **Claude 插件市场**：`~/.claude/plugins/`（已安装 `context7` 与 `skill-creator`，另含官方插件市场缓存共 2 个激活技能与数个草稿）；
  - **DSH Cordis 出厂预设**：`~/.dsh/profiles/` 与 `agent.cordis.yml` 自带技能（2 个预设专用技能）。
- **治理策略：只读索引与命名空间隔离**：
  - **命名空间与前缀隔离**：外部插件技能严禁剥离插件前缀散落在公共农场。例如 Claude 插件内的 `skill-creator` 必须通过 `plugin:skill-creator` 作用域调用，绝不进入公共软链农场；
  - **只读索引建立**：由 `assets-doctor` 在巡检时建立全局逆向索引，登记其逻辑名称与物理文件散列值；
  - **阴影风险（`shadow_risk`）判定**：
    若第三桶中的技能名称与第一桶（主库托管）或第二桶（保留内置）存在完全相同的无前缀名称，巡检器将其标记为 `shadow_risk: critical`，强制要求重命名插件调用别名或阻断分发。

### 2.4 全机技能对账机制、漂移检测与退出码分级

`assets-doctor` 作为统一巡检器，承担全机技能三桶对账机制：
1. **主库与农场对账**：检查 `agent-map.yaml` 中声明的各 Agent 软链接与文件系统真实链接是否 100% 吻合，严禁存在“死链（Dangling Symlink）”或“未登记孤儿软链（Orphan Symlink）”；
2. **三标记一致性校验（Triple-Flag Assertion）**：
   对于所有声明为 `role: member` 或独立 `load-mode: manual` 的技能，静态检查其物理文件：
   - 检查一：`SKILL.md` frontmatter 中必须包含 `metadata.load-mode: manual`；
   - 检查二：`SKILL.md` frontmatter 中必须包含 `disable-model-invocation: true`；
   - 检查三：`agents/openai.yaml` 中必须存在且满足 `interface.policy.allow_implicit_invocation: false`。
   三者有任一缺失或矛盾，视为契约破坏。
3. **漂移检测与退出码分级模型**：

```
                           ┌──────────────────────────┐
                           │    assets-doctor 巡检    │
                           └─────────────┬────────────┘
                                         │
                 ┌───────────────────────┼───────────────────────┐
                 ▼                       ▼                       ▼
           [ 致命阻断 ]             [ 警告与降级 ]            [ 全部通过 ]
         (Critical Failure)       (Warning / Drift)       (Healthy / Ok)
                 │                       │                       │
                 ▼                       ▼                       ▼
            退出码：2                退出码：1                退出码：0
     (契约断裂/破坏/死链)       (同名阴影/可恢复漂移)        (全绿/基线相符)
```

- **Exit Code 0（通过 / Success）**：
  全机软链 100% 对齐期望态，所有纳管技能三标记一致，外部 CLI 与必选 MCP 握手正常，无死链与冲突。
- **Exit Code 1（警告与可恢复漂移 / Warning & Drift）**：
  检测到良性漂移。例如：非关键 MCP 响应超时（走降级通道）、平台内置技能新增未审计项但未产生同名冲突、发现临时安装器着陆区存在非托管文件但未破坏现有农场。CI 模式下可通过报警通知人工干预，非阻断模式下允许执行。
- **Exit Code 2（严重契约阻断 / Critical Violation）**：
  破坏核心架构底线。包括：
  - 存在指向不存在物理路径的死软链；
  - `agent-map.yaml` 出现未定义族群引用；
  - 成员技能或 Manual 技能三标记断裂；
  - 第三桶插件技能与主库产生无隔离的同名阴影覆盖（`shadow_risk` 触发）；
  - `mcp-apply` 标记块遭到外部非法手工纂改且破坏闭合结构。
- **Exit Code 3（运行环境与内部异常 / Fatal Execution Error）**：
  巡检工具自身缺少必要依赖（如 pyyaml、tomli 丢失）、磁盘无法读写、宿主环境崩溃等非契约性底层执行异常。

## 三、AGENTS.md 统一项目指令标准与跨 Agent 记忆边界

### 3.1 AGENTS.md 实体升格与纯软链拓扑

历史架构中，仓库根目录存在 `AGENT.md` 作为物理文件，而 `CLAUDE.md` 与 `AGENTS.md` 作为软链接指向它。为对齐主流开源规范并消除多 Agent 识别歧义，全机实施指令标准化拓扑改造：

```
/home/dc/projects/dc-skills/
├── AGENTS.md           <=== 【唯一物理实体文件】（规范事实源）
├── CLAUDE.md           ───(软链接)───► AGENTS.md (兼容 Claude Code 官方加载规范)
└── AGENT.md            ───(软链接)───► AGENTS.md (兼容历史遗留脚本与规范)
```

- **统一标准**：将 `AGENTS.md` 升格为全局唯一的物理实体文件；
- **纯软链映射**：`CLAUDE.md` 和 `AGENT.md` 必须是以相对路径直接指向 `AGENTS.md` 的纯符号链接；
- **禁止双写**：任何自动化工具或人工操作严禁向 `CLAUDE.md` 或 `AGENT.md` 写入实体内容，违者在 `assets-doctor` 巡检中直接判定为 `Exit Code 2`。

### 3.2 指令与知识分离原则

严格界定“操作指令（Instructions）”与“领域知识（Domain Knowledge）”的物理与逻辑边界：
1. **指令留在 `AGENTS.md`**：
   - `AGENTS.md` 仅承载**Agent 行为准则、环境约束、绝对红线与高频工具使用铁律**。
   - 体积约束：物理文件行数控制在 150 行以内，内容精炼、语义无歧义。
   - 核心铁律包含：
     - 执行目录：Python 脚本一律先 `cd ~/projects/dc-skills` 再 `uv run`；
     - 输出规范：统一产物树，禁止污染工作区；
     - 真实产物验证：未调用写工具前严禁谎称完成。
2. **知识全部下沉至 `docs/` 与子规范**：
   - 凡涉及背景介绍、技术选型矩阵、架构演进推演、详尽配置参数、历史复盘等知识性内容，**一律从 `AGENTS.md` 剥离，下沉至 `docs/specs/`、`docs/arch/` 或 `docs/runbook/`**；
   - 在 `AGENTS.md` 中仅保留知识索引指向与绝对结论，杜绝知识冗余挤占上下文。

### 3.3 跨 Agent 三层记忆模型架构

为了在多个异构 Agent（Claude Code、Grok、Codex、DSH 等）之间实现既保持各模型推理独立性、又能共享全局知识与工程规范，制定全机标准三层记忆模型：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                       全机统一三层记忆体系架构                          │
├─────────────────────────────────────────────────────────────────────────┤
│ 【L1 层：私有会话与工作记忆】                                            │
│  • 归属范围：各 Agent 独立私有，互不干扰                                │
│  • 物理形态：                                                           │
│    - Grok:   /home/dc/.grok/memory-v2/ (global + workspace index)       │
│    - Claude: ~/.claude.json 中的 session transcript / auto-memory       │
│    - Codex:  ~/.codex/sessions/                                         │
│  • 治理约束：机器自动维护，禁止跨 Agent 直接读取或软链篡改              │
├─────────────────────────────────────────────────────────────────────────┤
│ 【L2 层：全机共享工程知识库】                                            │
│  • 归属范围：全机全模型只读共享                                          │
│  • 物理形态：统一 Markdown 知识库与规范资产                              │
│    - ~/.dsh/knowledge/ (如 config-files-guide.md)                       │
│    - ~/projects/dc-skills/docs/ (架构与规范唯一事实源)                  │
│  • 治理约束：通过 mdlineage 严格审计，具备稳定逻辑 ID，支持跨项目链接   │
├─────────────────────────────────────────────────────────────────────────┤
│ 【L3 层：项目指令与上下文基座】                                          │
│  • 归属范围：工作区级统一行为锚点                                        │
│  • 物理形态：各项目根目录下的 AGENTS.md                                  │
│  • 治理约束：Agent 启动自动吞吐，强制执行；仅放行动准则与红线            │
└─────────────────────────────────────────────────────────────────────────┘
```

- **L1（私有会话与工作记忆 / Private Working Memory）**：
  保存当前模型在特定任务中的上下文理解、草稿推演与短期偏好。其生命周期随会话重置或客户端自动维护，物理格式不一（如 Grok 的 SQLite/Markdown 混合 memory-v2、Claude Code 的本地 JSON 数据缓存）。**严禁任何外部脚本跨客户端挂载或直接覆写此区域**。
- **L2（全机共享工程知识库 / Universal Shared Knowledge）**：
  保存跨工具、跨项目通用的工程规范、架构基线与设计原则。以清晰结构化的纯 Markdown 形式组织，受 `mdlineage` 严格治理。所有 Agent 可在需要时主动按需索引与读取（例如通过 `read_file` 加载特定知识篇章）。
- **L3（项目指令基座 / Project Instructions Baseline）**：
  项目根目录下的 `AGENTS.md`。作为所有 Agent 进入工作空间后的第一道执行命令，是不可违反的底线准则。

### 5.2 mcp-apply.py 编译分发与安全标记块规范

为防止配置分发程序破坏用户的个性化配置，新增的 `scripts/mcp-apply.py` 严格遵循**安全标记块（Managed Content Blocks）**规范：

#### 1. 宿主文件与标记语法规范

- **Grok 配置（`~/.grok/config.toml`）**：
  采用 TOML 注释标记行：
  ```toml
  # BEGIN dc-farm mcp
  # Managed by dc-skills mcp-apply. DO NOT EDIT THIS BLOCK MANUALLY.
  [mcp_servers.codegraph]
  command = "codegraph"
  args = ["serve", "--mcp"]
  enabled = true

  [mcp_servers.keenable]
  url = "https://api.keenable.ai/mcp"
  enabled = true
  # END dc-farm mcp
  ```

- **Claude 配置（`~/.claude.json`）**：
  Claude 采用 JSON 格式，不支持注释标记块，因此采用**结构化字段隔离与合并策略**：
  在 `mcpServers` 字典内部，由 `mcp-apply.py` 读取原配置，比对 `agent-map.yaml` 中标记 `clients: [claude]` 的受控服务：
  - 受控键名完全由脚本全量同步与更新；
  - 非受控键名（用户手动添加的其他本地开发 MCP）**100% 严格保留，绝不触碰与删除**。

### 5.3 幂等性保障与自动回滚机制

`mcp-apply.py` 必须实现工业级事务保护与幂等机制：
1. **Dry-run 校验先行**：支持 `--dry-run` 参数，仅计算 Diff 并打印变更预览，不触发任何写操作；
2. **原子性写与备份（Atomic Write with Backup）**：
   - 写入前，对目标配置文件创建时间戳备份：`<config_file>.bak-<timestamp>`；
   - 先将结果写入临时文件 `<config_file>.tmp.<pid>`；
   - 执行静态解析自检（如 `tomli.loads` 或 `json.loads`），若解析失败立即中止并报错；
   - 通过 `os.replace` 原子替换原文件；
3. **闭合标记块完整性检查**：
   若目标文件中检测到 `# BEGIN dc-farm mcp` 但缺失 `# END dc-farm mcp`（标记块断裂），脚本立即抛出异常拒绝写入，防止破坏用户私有配置。

## 六、全机资产覆盖盲区与例外清单

全资产治理必须划定清晰的“可管”与“不可管”边界，对于客观存在但无法静态审计的资产建立明细账，防止巡检机制产生伪阳性（False Positives）。

### 6.1 动态与编译期内置盲区（不可静态审计资产）

以下资产由于其宿主架构实现特性，无法由静态代码或本地农场完成全面物理对账，列为已知盲区：

| 资产类型 / 名称 | 宿主位置 | 无法静态审计原因 | 治理与应对手段 |
|---|---|---|---|
| **Lark CLI 内置技能** | `lark-cli` 二进制可执行文件 | 28 个业务域技能在编译期静态打包进 Go 二进制文件（通过 `lark-cli skills read` 动态吐出），本地文件系统无独立 `SKILL.md`。 | 在农场中以单体技能 `lark-cli` 登记入库，视为黑盒黑体；版本随二进制工具链更新。 |

- **环境上下文**：WSL2 Linux 宿主与 Windows 宿主处于双系统并行状态。
- **治理规则**：

### 6.3 审计免死金牌（Explicit Exemptions）

`assets-doctor` 在执行全机扫描与漂移检查时，对以下特定目录与文件设立白名单免死金牌：

1. **安装器默认着陆区（`~/.agents/skills/`）**：
   - 允许存在通过通用安装器（如 `npx skills add`）临时拉取的第三方技能实验目录；
   - 巡检器仅输出 `info` 提示开发者手动收编，**绝不判定为漂移阻断（不报 🚨）**；
2. **Codex 系统专用技能目录（`~/.codex/skills/.system/`）**：
   - 属于 Codex 官方守护进程私有资产，`skills-sync` 与 `assets-doctor` 明确将其标记为只读忽略区，严禁尝试删除或软链篡改；
3. **DSH 预设只读资源（`~/.dsh/.agent-presets/*/skills/`）**：
   - 属于特定 Agent 预设绑定的专属技能（rank 300），受 `agent.cordis.yml` 托管，免于主库全局软链农场一致性强制约束。
