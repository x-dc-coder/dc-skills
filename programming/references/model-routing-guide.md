# 智能体团队模型路由与子代理派发规程

本规范定义智能体团队在派发子代理（Subagents）与执行复杂任务时的**模型选型标准**、**额度感知分层**与**双模型交叉审查流程**。

唯一事实源：`docs/arch/MODELS.md`。

---

## 1. 额度感知模型分层

各模型按照额度充裕度与核心能力分为三个梯队：

### 梯队 A：最高决策与核心分析层（稀缺额度 / 关键决策）
* **`grok-4.7`**（SpaceXAI 官方）：系统级宏观架构终审、极端跨系统故障排查、复杂安全威胁推演。
* **`glm-5.3`**（Z.ai Coding Plan 团队套餐）：深层根因分析定位、并发与数据流分析、落地工程可行性审查。
* *调用原则*：仅在初期方案定调、重大根因归纳与最终里程碑交叉审查时介入，限制其大篇幅代码生成以节省额度。

### 梯队 B：主力执行层（充足额度 / 大吞吐主力）
* **`deepseek-v4.1-flash`**（CommandCode GOAT 套餐，100万上下文 + 39万输出）：核心代码实现、详细排查步骤落地、测试用例编写。承担系统 80% 以上的代码与文本生成。
* **`gemini-3.8-flash`**（xlf 渠道，100万上下文）：大文件与代码库全景检索、前端页面与 UI 组件开发、多模态视觉验收、快速初审。

### 梯队 C：专项质检与免费探索层（专项能力 / 零额度消耗）
* **`step-5-preview`**（StepFun 本地 shim）：对抗质检工程师。专精红绿先验测试与变异反证（Mutation Testing）。
* **`Atria-Dawn-Preview`**（上海 AI 实验室 744B MoE，限时免费）：长程探索调研、开源方案比对、免费二线分析与初审节点，有效节约付费额度。

## 2. 子代理派发前健康探测（防序列化崩溃）

在向未经常调用的自定义模型派发大任务前，必须确保目标模型网络与反序列化解析通畅：

```bash
cd ~/projects/dc-skills && uv run python scripts/check_models.py -m <model-slug>
```

该脚本会以 Grok CLI 端到端流式执行检测，识别潜在的序列化错误（如 `reasoning_part`、缺失 `signature`、TLS EOF）并确认接口返回正常。

## 3. 双模型交叉审查操作标准（Cross-Verification Workflow）

所有关键架构方案、核心算法实现、PR Diff 审查与重大缺陷排障均执行双模型闭环：

```
                    ┌───────────────────────────────┐
                    │  Leader (主会话：意图分类与编排)│
                    └──────────────┬────────────────┘
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
       [1. 主执行子代理 Primary]       [2. 异构交叉审查 Cross-Review]
       (通常选用 ds 或 gemini)         (选用 glm / grok / atria / step)
       生成方案/代码/排查中间证据       独立审视、提出反例、挖掘盲区与漏洞
                    │                             │
                    └──────────────┬──────────────┘
                                   ▼
                    [3. 主智能体裁决与集成 Integration]
```

1. **主执行落地**：指派主力模型（`deepseek-v4.1-flash` 或 `gemini-3.8-flash`）生成产物，写入工作树或临时交换文件。
2. **异构交叉审查**：指派来自不同厂商/架构的模型作为对抗审查者，注入如下标准提示词头：
   ```markdown
   [ROLE: Adversarial-Reviewer]
   [TARGET: 审查以下产物，以批判性与对抗视角找出隐藏缺陷、未覆盖边界、潜在并发隐患或过度设计]
   ```
3. **主智能体裁定**：审查模型提出合理阻断意见时，组织主力模型完成一次修正收敛。

详细矩阵见 `docs/arch/MODELS.md`。核心高频场景速查：

| **核心算法与高难度业务** | `deepseek-v4.1-flash` (`high`) | `glm-5.3` (`high`) 方案指导 + `step-5-preview` (`high`) 边界交叉 |

## 5. 外部终审与逃生通道（Human-in-the-Loop: gpt6Astra）

用户配置有 ChatGPT Plus 会员，可手动使用 `gpt6Astra`。

### 触发条件
1. 团队内双模型交叉审查产生重大理论分歧且无法收敛。
2. 遇到现有所有模型均无法突破的未知底层设计瓶颈或深层次技术死锁。
3. 用户明确要求请求最高级别专家介入。

### 交互标准
当命中上述条件时，主智能体**停止盲目试错**，在当前会话直接输出一份格式化的《外部专家咨询卡》，提示用户手动前往客户端向 `gpt6Astra` 提问：

```markdown
### 📋 外部专家咨询卡 (针对 ChatGPT Plus / gpt6Astra)

**1. 问题背景与业务上下文**
[简要描述当前模块功能与技术栈]

**2. 核心冲突 / 阻断焦点**
[说明当前主要争议点、尝试过的方案以及为何陷入死锁]

**3. 对比方案简述**
- 方案 A (由 xxx 模型主张)：[要点与优缺点]
- 方案 B (由 yyy 模型主张)：[要点与优缺点]

**4. 恳请 gpt6Astra 裁决的明确问题**
- [具体问题 1]
- [具体问题 2]
```

用户将 `gpt6Astra` 的回答粘回当前会话后，主智能体作为最终权威决策执行落地。
